# 数学建模竞赛复盘与下次复用清单

本文沉淀一次完整数学建模竞赛中从读题、建模、计算、写作到定稿的可复用经验。核心目标是降低评委的认知成本，同时保证题意、模型、代码、结果、图表和论文之间能够逐项追溯。

## 1. 总体原则

1. **先锁定题意和信息边界，再选模型。** 每个决策时刻能使用什么数据必须写清楚，不能用事后信息反推事前方案。
2. **先形成统一主线，再逐问递进。** 各问应共享变量、约束或评价逻辑，避免成为互不关联的模型拼盘。
3. **模型复杂度服从题目需要。** 基线模型负责可解释和可提交，改进模型只解决真实痛点，复杂算法名称本身不构成创新。
4. **结论必须经过证据链。** 题目要求、模型定义、运行结果、验证证据、图表和论文表述必须一致。
5. **写作采用章节门控。** 先完成并核对一章，再进入下一章；全文完成后再做统一编号、引用和口径核验。

## 2. 推荐推进顺序

### 2.1 读题与任务对齐

- 把每一问拆成输入、决策变量、目标、约束、输出和指定交付格式。
- 区分题目明确要求与自行增加的分析，指定结果表不得为压缩篇幅而省略。
- 标出各问继承关系，特别检查时间尺度、边界状态、单位和评价口径是否改变。
- 建立“不能使用的信息”清单，防止数据泄漏和事后诸葛亮式建模。

### 2.2 模型设计

每一问先形成“基线—改进—防守”结构：

- 基线：贴题、稳定、可解释，构成最低可提交方案。
- 改进：针对误差、风险、动态更新、非线性、多目标或鲁棒性等真实困难。
- 防守：约束核验、基线对照、参数敏感性、极端情景或最优性边界。

重要模型应在逐条解释后增加“模型总括”，让读者一眼看到整体结构。推荐写成：

1. 目标函数；
2. 决策变量说明；
3. 按功能分组的核心约束；
4. 参数和变量边界。

总括式不使用跨越整组公式的巨大左大括号。采用“目标函数 + 分组约束”的 `aligned` 结构，并在正文中解释各组含义。总括式用于汇总，不替代前面对关键公式的推导和解释。

### 2.3 计算与结果管理

- 求解代码只负责计算，绘图代码只读取结果并作图，避免两处重复实现模型。
- 每次正式运行记录输入版本、参数、随机种子、时间戳、输出路径和关键指标。
- 明确唯一结果真源。正式提交工作簿或最终结构化结果确定后，由它反向核对 JSON、图表和论文，不能让旧缓存继续支撑正文。
- 对“全年为 0”“约束始终不触发”等结果必须解释机制，不能只报数值。
- 论文中描述模型或算法如何运行，不写“代码在某时刻截取”“代码令变量为”等实现口吻。

### 2.4 验证与一致性核验

至少完成以下检查：

- 量纲、时间步长和索引范围一致；
- 能量守恒、流量平衡或其他核心恒等式闭合；
- 状态初值、末值和滚动更新连续；
- 所有变量上下界与题设一致；
- 基线与改进模型使用相同评价口径；
- 摘要、正文、表格、图注、结论和附件数值一致；
- 强结论有基线、消融、敏感性或情景证据支持；
- 引用文献真实支撑相邻表述，正文引用和文末条目双向对应。

## 3. 动态决策问题的关键经验

### 3.1 信息可得性必须形式化

为每个决策时刻定义信息集，并明确预测、计划、修正、执行和事后评价各自允许使用的数据。实测轨迹通常不参与计划及修正方案的生成，只能用于：

- 后验补救评价；
- 费用或绩效结算；
- 状态变量更新；
- 后续决策时刻已经实现信息的更新。

摘要、模型假设、各问正文和代码实现必须使用同一口径。

### 3.2 规划时域与执行时域要分开

滚动优化中至少区分：

- 用于评估末端状态价值的预测或规划时域；
- 当前真正执行并锁定的时段；
- 下一次更新时重新优化的剩余时段；
- 当日或全周期末端状态约束。

不能把“跨日规划”误写成“每次修正都执行到跨日终点”。论文写模型如何更新，代码索引只作为核验依据。

### 3.3 创新应由决策价值证明

预测或信息更新类问题不能只比较 MAE、RMSE 等预测误差，还应评估它是否改变了决策。优先报告：

- 总成本或收益变化；
- 高价补救、紧急资源或违约风险变化；
- 约束违背次数和幅度；
- 状态安全裕度；
- 相对基线的稳定性。

真正有说服力的创新通常表现为“信息边界更严格、跨期价值处理更合理、风险指标更贴近决策”，而不是单纯更换算法名称。

## 4. 论文结构与压缩规则

### 4.1 标题层级

- 三级标题按真实写作任务设置，每章通常不超过 4 个，确有需要可到 5 个，但不固定凑数。
- 标题应体现本节内容，例如“滚动修正机制”“结果与风险分析”，避免“模型分析一”“进一步讨论”等空泛标题。
- 没有新结论或证据的“推广价值”“使用边界”等章节可并入模型评价，不单独占节。

### 4.2 模型假设与符号说明

- 假设采用“假设1：假设……”的短句格式，一条只表达一个核心前提。
- 假设只保留会改变模型结构、数据使用或结论边界的内容。
- 符号表删除“类别”列，只保留符号、含义和必要单位。
- 删除符号表前后无信息量的过渡句；符号说明不计入正文结果表编号。

### 4.3 篇幅压缩

- 先确定页数预算，再按章分配，不在最后一次性猛删。
- 单轮压缩建议不超过原文的 20%—30%，逐章确认后再继续。
- 优先删除重复背景、重复定义、重复结论、代码实现细节和无证据形容词。
- 不压缩题目指定结果、模型总括、关键约束、创新解释、异常机制和验证结论。
- 总括式存在的意义是降低检索成本；若只剩总括式而没有解释，或只有散式而没有总括，都不完整。

## 5. 公式与 MathType 兼容

- 两个及以上紧密相关的公式可用圆括号或分组环境组织，但必须逐一检查左右括号闭合。
- 优先使用常见的 `aligned`、`cases`、上下标、分式和求和符号，避免依赖冷门宏包或复杂嵌套命令。
- 不把编号、中文长句或说明文字塞进公式内部；公式之后用正文解释。
- 分段定义用 `cases`，模型汇总用 `aligned`；两者用途不同。
- 粘贴到 MathType 后重点检查：大括号、绝对值、范数、上下标、矩阵换行、中文标点和公式编号。
- 每次批量改公式后搜索不成对的 `\left`/`\right`、花括号和环境起止标记，并在 Word 中抽样打开验证。

## 6. 表格策略

- 题目指定的结果表必须完整给出，不能改成纯文字。
- 全文表格数量以信息密度为准，通常控制在约 5—7 个主要表；必要时用一个总表下设 `(a)(b)(c)` 紧凑子表。
- 自设宽表优先拆成纵向子表、减少重复列名、统一小数位和单位。
- 表号从问题一的第一张正式结果表开始；符号说明表不参与编号。
- 表应靠近首次解释它的正文，不把一章的图表全部堆在末尾。
- 图与表相邻时，中间至少安排一小段约两行的解释文字，使二者各自有论证角色，而不是机械留白。

## 7. 图片与图注策略

- 每张正文图必须有图注，并在正文中先解释“为何看这张图”，图后说明“它证明了什么”。
- 先设计图表证据链，再写绘图代码；没有对应结论的图不进入正文。
- 时间序列、状态轨迹和机制关系优先用图，精确指定结果和少量关键数值优先用表。
- 所有正式图统一输出 SVG 和高分辨率 PNG；SVG 用于 Word 缩放，PNG 作为兼容备份。
- 字号必须按插入 Word 后的实际物理尺寸检查。源图画布大并不等于正文中文字清楚。
- 放大字体后同步检查图例、坐标刻度、轴标题、注释、边距和子图间距，防止遮挡和挤压。
- 生成后必须逐张浏览，不以“代码成功运行”或“文件存在”代替视觉验收。
- 全部分问采用同一字体、色板、线宽、单位格式和导出策略，不能只优化第一问。

## 8. 引用与语言规范

- 参考文献引用属于证据链，压缩文字或调整章节时不要随意移动、删除或更换编号。
- 优先使用官方规则、原始论文、标准或权威资料；每条引用必须支撑相邻论断。
- 论文描述“模型”“算法”“求解过程”，不描述“代码怎么写”。
- 避免无证据使用“最优、显著、鲁棒、稳定、普适”等强词。
- 局限性应写清适用条件和失效边界，但不要用空泛自我否定削弱已被验证的结论。

## 9. 定稿前的交叉核验清单

### 9.1 题目符合性

- [ ] 每一问都有明确回答和指定交付物。
- [ ] 题目要求的日期、区间、表格和精度均已覆盖。
- [ ] 自增内容没有挤掉必答内容。

### 9.2 数学与算法

- [ ] 目标函数、决策变量、约束和参数边界在模型总括中齐全。
- [ ] 详细公式与总括式完全一致。
- [ ] 时间步长、索引终点和滚动区间与代码一致。
- [ ] 信息集没有使用未来实测数据。
- [ ] 特殊的零值、突变和边界解已有解释。

### 9.3 结果与证据

- [ ] 正文数值来自唯一最终结果源。
- [ ] JSON、工作簿、图表、摘要和结论无旧版本残留。
- [ ] 每个创新点在分析、模型、结果图表和验证中形成闭环。
- [ ] 每个核心结论至少有一个可追溯证据。

### 9.4 排版与表达

- [ ] 三级标题数量合理且名称具体。
- [ ] 假设简洁，符号表无冗余列和无关符号。
- [ ] 表号、图号、公式号和交叉引用连续。
- [ ] 所有图有图注，图中文字在 Word 实际尺寸下清晰。
- [ ] 图表没有集中堆放，相邻图表间有解释文字。
- [ ] 公式可在 MathType 正常录入，括号与环境闭合。
- [ ] 参考文献正文引用与文末条目一致。

## 10. 下次比赛的最小执行清单

1. 初始化赛题专属目录，原始数据只读保存。
2. 完成任务对齐和信息边界表，确认后再建模。
3. 每问先做可解释基线，再决定是否增加改进模型。
4. 定义结果真源和运行记录格式，避免中途产生多套口径。
5. 在绘图前列出“结论—图表—数据源—正文位置”映射。
6. 每问完成后核验模型、代码、结果和文字，再进入下一问。
7. 论文逐章生成、逐章压缩，保留模型总括和题目指定结果。
8. 最后统一进行数学、数值、图表、引用和 Word 实际版面核验。

这份清单应随下一次比赛继续增补，但新增规则必须来自真实问题或复盘证据，避免把偶然的单题写法固化为所有题型的强制模板。
